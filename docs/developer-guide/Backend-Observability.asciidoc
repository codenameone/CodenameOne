[[backend-observability]]
== Backend tracing, metrics and management

A server in production has to answer three questions for whoever runs it: what did
this request do, how's the server doing, and what can be changed without
redeploying. Traces answer the first, metrics the second, and managed beans the third.
All three follow the OpenTelemetry conventions, so they reach whatever
observability stack a deployment already runs, and all three are linked into the
binary only when the build is asked for them.

=== Tracing with OpenTelemetry

A server can report every request it serves to any OpenTelemetry collector, and
the reporting needs no code in the handlers. Turn it on at build time with the
annotation, on any class in the backend module:

[source,java,role=cn1-no-try]
----
include::../demos/backend/src/main/java/com/codenameone/developerguide/backend/TracingSnippets.java[tag=backend-otel-annotation,indent=0]
----

Without touching the source, set it in `application.properties` instead:

----
cn1.otel.enabled=true
----

Either one makes the generated entry point install a tracer. From then on:

* every request is a server span, named after the route that matched
  (`GET /notes/{id}`), with its status, method and path;
* every outbound `Web` call is a client span, and sends the W3C `traceparent`
  and `tracestate` headers so the service it reaches joins the same trace;
* every `Database` statement is a client span carrying the SQL as the code wrote
  it, placeholders and all -- the bound values are never recorded;
* an incoming `traceparent` makes the request part of the caller's trace, which is
  how a Codename One app's spans connect to the backend's own (see
  <<opentelemetry-tracing>>).

A WebSocket connection isn't a span. It can stay open for hours and carry any
number of messages, so it has no single start and end to time, and its upgrade
request is answered before tracing begins.

Without the annotation or the property, nothing refers to the tracer and the
translator leaves it out of the binary.

`cn1.otel.enabled` is a build-time setting: the build reads it from the module's
properties files. A server built without the exporters that finds it `true` at
run time, in the environment or a properties file beside it, doesn't start, and
the error says where the key belongs. A server built with them that finds it
`false` at run time exports nothing. See <<backend-build-time-settings>>.

Spans go out over OTLP/HTTP, as binary protobuf by default, batched on a
thread of their own so a slow collector never holds up a request. A queue that
fills because the collector is down drops spans and counts them, and
`HttpServer.getMetrics()` reports those counts. The settings are the standard
OpenTelemetry environment variables, so a deployment configures this server the
same way it configures everything else it runs:

[cols="2,2,3"]
|===
| Variable | Property | Meaning

| `OTEL_EXPORTER_OTLP_ENDPOINT` | `cn1.otel.endpoint` | The collector's base URL; `/v1/traces` is appended. Defaults to `http://localhost:4318`.
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `cn1.otel.traces.endpoint` | The full URL, used as it is.
| `OTEL_EXPORTER_OTLP_HEADERS` | `cn1.otel.headers` | `name=value` pairs, comma separated, with each value URL-encoded.
| `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | `cn1.otel.traces.headers` | Headers for traces only, in place of the shared ones.
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `cn1.otel.protocol` | `http/protobuf` or `http/json`. gRPC isn't supported.
| `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` | `cn1.otel.traces.protocol` | The protocol for traces only.
| `OTEL_SERVICE_NAME` | `cn1.otel.service.name` | Overrides the annotation's `serviceName`.
| `OTEL_RESOURCE_ATTRIBUTES` | `cn1.otel.resource.attributes` | Extra resource attributes, `key=value` pairs.
| `OTEL_TRACES_SAMPLER` | `cn1.otel.sampler` | `parentbased_always_on` by default; also `always_on`, `always_off`, `traceidratio` and the other `parentbased_` forms.
| `OTEL_TRACES_SAMPLER_ARG` | `cn1.otel.sampler.arg` | The ratio for the ratio samplers.
| `OTEL_SDK_DISABLED` | `cn1.otel.disabled` | `true` turns tracing off at start-up without a rebuild.
| `OTEL_BSP_MAX_QUEUE_SIZE` | `cn1.otel.queue.size` | Spans held for export before new ones are dropped. Defaults to 2048.
| `OTEL_BSP_MAX_EXPORT_BATCH_SIZE` | `cn1.otel.batch.size` | Spans sent in one export. Defaults to 512.
| `OTEL_BSP_SCHEDULE_DELAY` | `cn1.otel.export.delayMillis` | Milliseconds between exports. Defaults to 5000.
|===

`cn1.otel.attributes.exclude` names attributes never to record, for example
`db.query.text` in a code base that builds SQL by concatenating values.

Sending spans to Dynatrace, which accepts OTLP over HTTP as protobuf, is a
matter of pointing the endpoint at the environment's OTLP API and passing an
ingest token:

----
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://abc12345.live.dynatrace.com/api/v2/otlp/v1/traces
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Api-Token%20dt0c01.XXXX
----

Under Lambda, the invocation continues the trace the host passes in its X-Ray
header, and the loop waits for the export before it polls again, because the host
freezes the process between invocations.

`Tracing.current()` returns the request's span, for adding an attribute of the
application's own, and `Tracing.inSpan` times a block of work as a child span.

==== Relaying the app's spans

A mobile app shouldn't carry the collector's credentials: anything inside an app
package can be read by whoever installs it. With `cn1.otel.relay=true` the backend
accepts the app's spans at `/otel/v1/traces` (`cn1.otel.relay.path` moves it), adds its own credentials and
forwards them to the same collector:

----
cn1.otel.relay=true
# Optional: a shared secret the app sends in X-CN1-Telemetry-Token.
cn1.otel.relay.token=${RELAY_TOKEN}
# Only for a web app served from another origin.
cn1.otel.relay.corsOrigin=https://app.example.com
----

The relay takes OTLP/JSON, rebuilds it against the OTLP schema -- a field the
schema doesn't name is dropped and a malformed id is refused -- and queues it for
export in whatever protocol the server exports with. It answers as soon as the
spans are queued, and answers 503 when the queue is full so the app backs off.
`cn1.otel.relay.maxBytes` and `cn1.otel.relay.maxSpans` bound a single export.

=== Metrics and management

Traces say what one request did; metrics say how the server is doing. With
OpenTelemetry turned on, the server exports metrics over OTLP on the same endpoint
and with the same settings as its traces, every minute by default, with cumulative
temporality. `cn1.otel.metrics.enabled=false` turns metrics off while leaving
traces on. The management endpoints described below record and serve the same
metrics whether anything exports them or not.

The route attribute is the template -- `GET /notes/{id}` is recorded as
`/notes/{id}` -- so a server's metric count doesn't grow with the ids its clients
ask for. A request that fails, whether in a handler or in the session store, is
recorded with status 500.

`GET /manage/schema` returns this table for the running server as JSON: its
runtime (`jvm` or `native`) and, for each metric, its kind, unit, attributes,
temporality, Micrometer name and whether this server measures it.

==== Unavailable is not zero

A metric a server can't measure isn't reported as `0`. Its instrument isn't registered, or reads
no value, so it's absent from the JSON view, the Prometheus scrape and the OTLP
export, and `/manage/schema` lists it with `"available": false` and the reason.
On a packaged server that means the JVM-only rows above; on a server with no
database it means the pool rows. A gauge whose source can't be read at collection
time is likewise left out rather than written as zero. An alert on "thread count is
0" therefore never fires on a native server by accident: query the series' absence
instead, or read the schema.

The schema also lists, under `unmeasured`, the Micrometer meters a Spring Boot
dashboard commonly reads that neither runtime reports, each with its reason:
`jvm.gc.pause` as a per-pause histogram, `jvm.gc.memory.allocated` and
`jvm.gc.memory.promoted`, per-pool `jvm.memory.used`, `jvm.buffer.memory.used`,
`jvm.threads.states`, `process.cpu.usage`, `system.cpu.usage`,
`system.load.average.1m`, `process.files.open`, `hikaricp.connections.usage`,
`hikaricp.connections.acquire` and `logback.events`.

==== Moving a Spring Boot dashboard

The Micrometer column says which series to switch to. In Prometheus form a name's
dots become underscores, so a panel on `hikaricp_connections_active` reads
`db_client_connection_count - db_client_connection_idle`, one on
`http_server_requests_seconds_count` reads `http_server_request_duration_count`,
and `tomcat_connections_current_connections` becomes
`http_server_open_connections`. Two differences to adjust for:

* **Units.** Durations are milliseconds, not seconds, so a latency threshold of
  `0.5` becomes `500`, and histogram buckets are in milliseconds.
* **Attribute names.** Requests carry the OpenTelemetry attributes
  `http.route`, `http.request.method` and `http.response.status_code` rather than
  Micrometer's `uri`, `method` and `status`.

`vm/backend/dashboards/backend-overview.json` in the Codename One repository is a
Grafana dashboard written against the schema: request rate, latency percentiles,
errors, connections, the database pool, executors, scheduled jobs, memory and
uptime. Import it and pick the Prometheus data source that scrapes
`/manage/prometheus`. It uses only metrics every runtime measures, so its panels
are filled on the JVM and on a packaged server alike.

==== Managed beans

The application's own metrics follow the JMX model -- attributes to watch and
operations to call -- with Spring's annotations for it:

[source,java,role=cn1-no-try]
----
include::../demos/backend/src/main/java/com/codenameone/developerguide/backend/beans/PriceCache.java[tag=backend-managed,indent=0]
----

`@ManagedResource` marks the bean, and `objectName` names it; without one it's
the simple class name. The name is a segment of the management URL, so it's made
of letters, digits, `_`, `-` and `.` only. Each `@ManagedAttribute` is an instance getter with no
parameters, and a numeric one becomes a gauge named after the resource and the
attribute -- `prices.size` here -- read each time metrics are collected. Every
attribute, numeric or not, appears in the management listing. A
`@ManagedOperation` is a method an operator can call, whose parameters may be
strings, numbers, booleans, and enums. An operation's parameters are named by
`@McpParam` when they carry one, and otherwise `arg0`, `arg1`, in order. The build
checks each of these rules and refuses a managed method on a class with no
`@ManagedResource`. It also refuses a managed resource that isn't a singleton,
because metrics are read outside any request or session. An operation is invoked
by name, so it refuses an overloaded one too.

`@Timed` records each call's duration as a histogram, and `@Counted` counts calls,
with a second counter for the failures. Their instruments are named after the class and method
unless the annotation's `value` names them:

[cols="1,2", options="header"]
|===
| Annotation | Instruments

| `@Timed`
| `<class>.<method>.duration`, a histogram in milliseconds

| `@Counted`
| `<class>.<method>.calls`, and `<class>.<method>.calls.failures` for calls that threw
|===

`<class>` is the fully qualified class name. Like `@Transactional`, they're woven
into the method at build time, so a call through `this` is measured too.

Metrics use the tracing settings from <<Tracing with OpenTelemetry>> unless a
metrics-specific one is set, which is the precedence the OpenTelemetry
specification gives:

|===
| Variable | Property | Meaning

| `OTEL_METRIC_EXPORT_INTERVAL` | `cn1.otel.metrics.intervalMillis` | How often to export, in milliseconds. A minute by default.

==== Management endpoints

The management endpoints make the same information available over HTTP, for a
load balancer and for an operator:

----
GET  /manage/health        public; 503 while starting or draining
GET  /manage/health/liveness   public; 200 while the process serves at all
GET  /manage/health/readiness  public; 503 while starting or draining
GET  /manage/schema        the metric schema, as JSON
GET  /manage/metrics       every metric, as JSON
GET  /manage/prometheus    every metric, in the Prometheus text format
GET  /manage/jobs          the scheduled jobs and their last runs
GET  /manage/managed       the managed beans and their attributes
POST /manage/managed/{bean}/{operation}
----

An operation's body is a JSON object of its arguments by parameter name. A body
that isn't one, or an argument the operation refuses, is answered with 400; 404
means only that no managed bean or operation has that name. Two managed resources
with the same `objectName`, or two `@McpTool` methods with the same name, are a
build error, since each is found by that name.

Health reports `STARTING` until the server has finished starting, including the
application's scheduled jobs and exporters, `UP` while it serves, and `DRAINING`
once it's stopping. The listener accepts connections before start-up finishes, so
a load balancer that checks health doesn't send traffic to a server that may
still fail to start.

[cols="2,3", options="header"]
|===
| Key | What it sets

| `cn1.management.enabled`
| Whether the endpoints are served. On by default on a development profile, off
  everywhere else. Build-time: `true` in the module's properties files is what
  links the endpoints into a packaged server.

| `cn1.management.token`
| The bearer token every endpoint but health and the probes requires, sent as
  `Authorization: Bearer <token>`. A missing or wrong token is answered with 401, and an operation on a server
  that has no token set with 403. Outside a development
  profile the server refuses to start with the endpoints on and no token, since
  the metrics and managed beans would be readable by anyone who can reach the
  port.

| `cn1.management.path`
| Where the endpoints live, `/manage` by default.
|===

IMPORTANT: A packaged server has no management code at all unless its build asks
for it. The generated entry point is the only code that names the endpoints, and
it names them only when the build sees `cn1.management.enabled=true` in
`application.properties` or a profile's file. Without it, the translator leaves the endpoints out of the binary, so there's
no `/manage` to find or to misconfigure, whatever profile the server later runs
under. The development run through `cn1:backend` always builds them in.

[source,properties]
----
include::../demos/common/src/main/snippets/developer-guide/backend-observability.properties[tag=backend-observability-properties-001,indent=0]
----

A server built with them can still turn them off at start-up with
`cn1.management.enabled=false`. A server built without them that finds
`cn1.management.enabled=true` at run time doesn't start, because there's nothing
to turn on, and the error says that the key belongs in the module's
`application.properties`. See <<backend-build-time-settings>>.

On a development profile without a token, the read-only views are open to anyone
who can reach the port, which is a laptop. An operation needs the token on every
profile, because it changes the running server.

==== Probes and draining

The two probes follow the split Kubernetes and Spring Boot's
`/actuator/health/liveness` and `/actuator/health/readiness` make. Liveness says
the process is running and answering, and stays 200 while it starts and drains;
point a liveness probe at it, so a slow start or a drain never gets the container
restarted. Readiness is 503 until start-up finishes and again from the moment the
server begins to stop; point a readiness probe or a load balancer health check at
it. `/manage/health` answers as readiness does, with the state in the body.

When the server is told to stop (SIGTERM, or the platform's equivalent), it turns
readiness to 503, stops accepting new connections, lets the requests in flight
finish within `cn1.server.shutdownTimeoutMillis`, runs the exporters' last export,
and exits. Give the platform's termination grace period a few seconds more than
that timeout. The probes need no token on any profile, since a load balancer has
none to send.

Health answers 503 while the server drains, so a load balancer stops sending it
new requests before it stops accepting them. The Prometheus view turns each name
into a Prometheus one, replacing the dots with underscores and adding `_total` to a
counter, so `http.server.request.duration` is scraped as
`http_server_request_duration`.

The management endpoints are served before the application's routes, so a
catch-all route can't answer them.

=== Application caches

`Cache` keeps values a server would otherwise fetch or compute again, with a bound
on how many it holds and how long each one lives. It's plain Java, so the same cache
runs on the JVM and in the packaged native server:

[source,java,role=cn1-no-try]
----
include::../demos/backend/src/main/java/com/codenameone/developerguide/backend/CacheSnippets.java[tag=backend-cache,indent=0]
----

A builder sets the bounds, and nothing is bounded unless it's asked for:

[cols="2,5"]
|===
| Setting | Meaning

| `maximumSize(n)` | At most `n` entries; the least recently used go first.
| `maximumWeight(w, weigher)` | At most `w` in total, as the weigher weighs each entry. An entry heavier than the whole bound isn't kept: it's reported as a `SIZE` removal, and the other entries stay.
| `expireAfterWriteMillis(ms)` | An entry lives this long after it's stored.
| `expireAfterAccessMillis(ms)` | An entry lives this long after it was last read or stored.
| `expiry(expiry)` | Each entry's lifetime, chosen when it's stored. It replaces the write lifetime for that entry; the access lifetime still applies. A lifetime of zero or less isn't stored and removes the key's old value, so a `get` of such a value calls its loader every time.
| `removalListener(listener)` | Called for every entry that leaves, with the cause: `EXPLICIT`, `REPLACED`, `EXPIRED` or `SIZE`.
| `clock(clock)` | Where the cache reads the time. Tests replace it to move time without waiting.
|===

==== Loading

`get(key, loader)` returns the entry, or runs the loader on the calling thread when
there's none. Requests asking for a key while its load runs don't load it again:
they wait for that load and get its result. A waiting request on a virtual thread
yields, so a slow load holds back only the requests that want its key.

A loader that throws stores nothing. Every request waiting for it gets the same
failure: an unchecked exception as it was thrown, a checked one wrapped in
`Cache.LoadException`. The next request loads again. A loader that returns null
stores nothing either. When the key is invalidated or `put` while its load runs,
the loaded value goes to the requests waiting for it and isn't stored over the newer
state. A loader can use the cache, but asking for its own key is refused rather than
waiting forever for itself.

The loader runs as part of the request that started the load, with that request's
transaction, security context and trace. The others only receive its value, so a
loader shouldn't return anything specific to one user.

==== Expiry and removal

An expired entry is never returned. It's removed when a read finds it, by a
periodic sweep during writes, or by `cleanUp()`. `size()` cleans up first, so it
counts live entries only.

The removal listener runs on the thread whose call removed the entry, after the
cache has released its lock, so it may use the cache. A listener that throws is
reported on standard error and changes nothing else.

==== Metrics

Every cache publishes its figures to `Metrics` under its name:

[cols="2,1,4"]
|===
| Name | Kind | Meaning

| `cache.<name>.hits` | counter | Lookups answered from the cache.
| `cache.<name>.misses` | counter | Lookups that weren't.
| `cache.<name>.loads` | counter | Loads that finished, including those that returned null.
| `cache.<name>.load_failures` | counter | Loads that threw.
| `cache.<name>.evictions` | counter | Entries removed for the size or weight bound.
| `cache.<name>.load.duration` | histogram | Time spent in the loader, in milliseconds.
| `cache.<name>.size`, `.weight` | gauge | Entries held, and their total weight.
|===

The same figures are on the cache itself, from `hitCount()` to `evictionCount()`.
Give each cache its own name; two caches with one name share the counters.

==== Scope and memory

A cache belongs to one process. Two instances of a server each hold their own, and
invalidating a key in one doesn't reach the other. Values are held by reference, so
treat them as read only.

Each entry costs about a hundred bytes beyond its key and value: a map entry with
its links in access order, and a node holding the value, its weight and its
timestamps.
