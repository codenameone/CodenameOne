== Embedded Linux devices

Codename One runs on embedded Linux boards -- Raspberry Pi, NXP i.MX, Rockchip,
NVIDIA Jetson, BeagleBoard, RISC-V boards -- as the same single native binary the
<<_working_with_the_native_linux_port,native Linux port>> builds, with the desktop
layer swapped out. There is no X11, no Wayland compositor, no GTK and no JVM on the
device: the application takes the screen directly through the kernel, reads touch,
keys and rotary encoders straight from the input devices, and starts from boot as a
service.

The same source is also the phone, tablet and desktop companion application. A
form, a theme, an entity model or a REST client written for the device builds for
iOS and Android unchanged, and the simulator runs it on the desktop with a virtual
board attached.

=== Why use Codename One on a device

* *One native executable.* ParparVM translates the application, Codename One and
  the Java runtime it uses to C, and the board's compiler builds it. Nothing is
  interpreted and nothing is compiled at start-up, so the first frame arrives in
  tens of milliseconds and memory use stays flat.
* *Java or Kotlin for the whole product.* The device UI, the companion application
  and, with the <<_server_side_backend,backend>>, the server or the headless gateway share one
  language, one build and one set of classes.
* *A renderer that owns every pixel.* Codename One draws its own components, so the
  user interface looks the same on a 3.5 inch SPI panel, a 10 inch HMI and a phone,
  and it needs nothing from the board but a frame buffer.
* *Hardware access in the core API.* GPIO, I2C, SPI, serial ports, PWM, CAN, the
  watchdog and the backlight are `com.codename1.hardware`, implemented in the port,
  with virtual devices in the simulator.

=== Displays and the software fallback

At start-up the port picks the first display back end that works, in this order,
and every board renders through at least the last two:

. *DRM/KMS* (`/dev/dri/card*`): a mode is set on the first connected output and
  frames are flipped between two buffers, so there is no tearing. This is the path
  on Raspberry Pi 4 and 5, i.MX 8, Rockchip and any board with a modern display
  driver.
. *fbdev* (`/dev/fb0`): the legacy frame buffer, at 32 or 16 bits per pixel, for
  SPI panels and older kernels.
. *Memory*: renders without a display, for tests, screenshots and benchmarks.

Rendering is in software, by a renderer built into the port, which needs no GPU
driver and is fast enough for a full-screen HMI at 60 frames per second on a
Raspberry Pi class board. Text is drawn with FreeType and images are decoded with
libpng and libjpeg; nothing of a desktop stack (X11, GLib, Cairo, Pango or
FontConfig) is loaded, so the application starts in a few tens of milliseconds.
Images are PNG or JPEG.

Fonts are found by file name, without FontConfig: in the directories listed in
`CN1_FONT_PATH`, then in a `fonts` directory beside the executable, then under
`/usr/share/fonts` and `/usr/local/share/fonts`. The default face is DejaVu Sans,
or Liberation, Noto, FreeFont, Roboto or Open Sans when DejaVu is absent. Fonts an
application bundles work the same as on every other platform.
The `CN1_DISPLAY` environment variable forces a back end (`drm`, `fbdev`, `memory`
or `headless`); the others are listed in the table below.

.Environment variables read by the embedded port
[cols="<1,<3",options="header"]
|===
|Variable |Effect

|`CN1_DISPLAY` |`drm`, `fbdev`, `memory` or `headless`; by default the first that works
|`CN1_DRM_DEVICE`, `CN1_FB_DEVICE` |The device node to use instead of the first found
|`CN1_ROTATION` |`0`, `90`, `180` or `270`, for a panel mounted on its side
|`CN1_DPI` |The panel's density, when the display doesn't report its size
|`CN1_SIZE` |`800x480`: the size of a `memory` display
|`CN1_CURSOR` |`1` draws a pointer for a mouse; touch panels have none by default
|`CN1_TOUCH_SWAP_XY`, `CN1_TOUCH_INVERT_X`, `CN1_TOUCH_INVERT_Y` |Correct a touch controller mounted differently from its panel
|`CN1_INPUT_NO_GRAB` |`1` leaves the input devices shared with other processes
|`CN1_FONT_PATH` |Directories, separated by colons, searched for fonts before the system's
|===

Input comes from every `/dev/input/event*` device, including devices plugged in
later: multi-touch panels (with pinch), mice, keyboards and rotary encoders, which
move the focus like the arrow keys. Text fields open an on-screen keyboard, since
a device seldom has a physical one. `SIGTERM` closes the application cleanly and the
console is restored on exit.

=== GPU rendering

Boards with a dependable OpenGL ES 2 driver can draw through the GPU instead.
The same renderer still decides what every operation covers -- shapes, clips,
glyphs and antialiasing are computed exactly as in software -- and the GPU then
composites the result: fills, gradients, images and text become textured quads,
images are uploaded once and kept on the GPU, and the finished frame is flipped
to the display with no copy. The pointer moves on the display's cursor plane.
Frames are identical to the software renderer's; the CPU time a frame costs is
what drops, which matters most for large images, full-screen animation and
high-resolution panels.

The `linux.embedded.renderer` build hint chooses: `gpu` or `software`. Without
it, the board profile decides: `gpu` for the Raspberry Pi profiles, `imx8`,
`imx6`, `rk3588`, `jetson` and `generic-x64`, and `software` for the rest. A
`software` build links no GPU library at all.

A `gpu` build never fails to show a picture for want of a GPU. When the device
has no usable driver, or the driver can't draw the window, the application logs
the reason and continues with the software renderer. The first log line names the
renderer in use (`renderer gpu` or `renderer software`). The device needs Mesa's
GBM, EGL and GLES 2 libraries (`libgbm1`, `libegl1`, `libgles2` on Debian and
Raspberry Pi OS), or the board vendor's equivalents.

`linux.embedded.display`, `linux.embedded.rotation` and `linux.embedded.dpi` set
the defaults the binary starts with; the environment variables override them on the
device. `linux.sysroot` points a cross build at a Yocto or Buildroot SDK sysroot, so
the binary links against exactly the libraries the image carries.

The device needs FreeType, libpng, libjpeg, zlib, a font and, for DRM/KMS, libdrm.
OpenSSL 3 and libcurl are loaded only when the application first uses cryptography
or the network. Raspberry Pi OS Lite has most of them; the
`scripts/embedded/pios/setup-device.sh` script installs the rest and prepares the
device to start the application at boot.

It uses the system's `ssh`, so keys, agents and `~/.ssh/config` aliases
work as they do in a terminal. `cn1.device.env` passes environment variables to the
service (`CN1_ROTATION=90,CN1_DISPLAY=fbdev`), and `cn1.device.logs=true` follows its

For a production image, `scripts/embedded/yocto/meta-codenameone` is a Yocto layer
and `scripts/embedded/buildroot/package/codenameone-app` a Buildroot package. Both
build the translated application with the image's own toolchain and start it at
boot.

=== Hardware access

`com.codename1.hardware.Hardware` is the entry point. On a device it drives the
kernel's own interfaces -- the GPIO character device, i2c-dev, spidev, termios, sysfs
PWM and backlight, SocketCAN and `/dev/watchdog` -- with no extra library. On a phone
it reports no support, so the same code runs everywhere:

[source,java]
----
include::../demos/common/src/main/java/com/codenameone/developerguide/snippets/generated/EmbeddedLinuxJava001Snippet.java[tag=embedded-linux-java-001,indent=0]
----

Listeners run on the event dispatch thread. Reads that wait for data -- a serial
port, a CAN frame -- take a timeout and belong off the event dispatch thread.

The simulator attaches a virtual board: `gpiochip0` with 32 lines, a TMP102
temperature sensor at `0x48` and an EEPROM at `0x50` on I2C bus 1, loopback SPI,
serial and CAN devices, two PWM channels, a watchdog and a backlight. Hardware code
therefore runs, and can be unit tested, before a board is on the desk.

=== Headless devices with the backend

A gateway, a sensor hub or a controller with no screen runs the
<<_server_side_backend,backend>> instead: a native REST and WebSocket server, built the same way
and as small. `Hardware.getInstance()` works there too, through the same kernel code
as the UI port, and listener callbacks run on the pin's own thread. The device then
serves its API, the phone application is the client, and both share the entity
classes.

=== Finding each other on the network

Devices, phones and servers on one network find each other over multicast DNS
(Bonjour), so nobody types an address. The Linux port implements
`BonjourBrowser` and `BonjourPublisher` itself, on a plain UDP socket, so a
Buildroot image needs no Avahi. The backend has the same protocol as
`com.codename1.backend.Discovery`:
