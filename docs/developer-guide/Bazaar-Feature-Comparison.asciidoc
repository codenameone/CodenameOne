== Bazaar: Feature comparison

This chapter lists what Bazaar does next to the commerce platforms people most
often compare a store against: Shopify, WooCommerce, BigCommerce and Square
Online. For the point of sale rows, the Square column describes Square Point of
Sale. <<bazaar-users-guide>> describes each feature from the user's side, and
<<bazaar-implementors-guide>> explains how each one is built.

The tables read as follows.

* In the Bazaar column, &#10003; means supported, &#9681; means partly supported
  (the Notes column says what differs) and &#8211; means absent.
* In the other columns, "core" means the platform includes it and "app/plugin"
  means stores commonly add it through the platform's app store or plugin
  directory, and "no" means the platform has neither and stores generally
  cannot add it. An empty cell means the table makes no claim either way.
* Where Bazaar talks to an outside service, such as a card processor or a
  shipping carrier, it does so through an interface. The sample ships a
  simulated implementation beside the real one, and the Notes say so where it
  matters.

The other platforms change often. Check their own documentation before relying
on a row.

=== Beyond the usual feature list

Some of what Bazaar offers doesn't fit a row in the tables above, because it's
about how the platform is built and run rather than what a store sells.

* *One codebase for every client.* The same Java application runs on iOS,
  Android, the desktop and in a browser, for shoppers, staff and the
  administrator. The server is Java too, in the same Maven project.
* *A register that keeps selling offline.* Sales made with no network are kept
  on the device and sent when it reconnects. Each sale carries a client id the
  server stores as unique, so a batch sent twice records every sale once.
* *A browser-native storefront.* Product, collection, cart, checkout and account
  pages are server-rendered HTML that works without the app, with titles,
  canonical links, structured data and a sitemap for search engines. Each page
  sends a Content Security Policy built from script hashes and a per-request
  nonce.
* *Sandboxed app slots.* An owner can place third-party snippets and widgets at
  named places of the storefront. Widgets run in a sandboxed frame, every change
  is audited, and scripts in an optional category load only after the visitor
  accepts that category in the cookie banner.
* *Journeys drawn as flowcharts.* Automations and customer journeys are graphs
  of triggers, waits, splits and messages, edited on a canvas, with per-step
  counts of who passed through.
* *Carts and orders on one board.* The sales pipeline puts every open cart
  next to every open order, scores each cart's purchase intent with reasons a
  merchant can read, and turns a drag into the action it stands for. The AI
  behind the assistant and the description drafts is the owner's choice of
  provider, its key never leaves the server, and the same screens work with no
  provider at all.
* *A Kanban board for fulfilment.* Orders move through columns from paid to
  delivered.
* *Charts drawn by the server.* The back-office dashboard draws its charts on
  the server, so they show in any browser with no chart library.
* *Documents as PDF files.* Invoices, receipts, pick lists and shipping
  labels are rendered as PDF files.
* *Any of four databases.* The same server and migrations run on SQLite,
  PostgreSQL, MySQL and MariaDB.
* *Self-hosted, with the source.* The whole sample is released under the MIT No
  Attribution license, so it can be copied, changed and run anywhere.
