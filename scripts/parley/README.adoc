= Parley

A private messenger and its server, in one Maven project and one language. People
chat one to one, in groups and in channels, send photos, video and voice notes,
and call each other with voice or video. Messages, attachments and calls are
end-to-end encrypted: the server stores and relays what it cannot read. An
administrator runs the service, with its statistics, its reports and its accounts,
without ever seeing a message. Which of these a person sees is decided by the roles
the server gives their account: a user opens on their chats, an administrator on
the admin console.

It is a sample of how a Codename One application and a Codename One Backend fit
together, and the project the Initializr generates when you start from the
messaging template.

== The modules

[cols="1,4"]
|===
| `shared`
| The contract: the data classes both sides exchange and the `@RestClient`
  interfaces that name every call. The app's build generates a client from them
  and the server's build generates the interfaces it implements, so a change the
  other side did not follow is a compile error.

| `common`
| The application: sign-in, the chats and their screens, the keys, sessions and
  encrypted vault in `crypto`, calls over `com.codename1.webrtc` and
  `com.codename1.call`, the privacy settings, the admin console and the live
  channel. Styled in `src/main/css/theme.css`, whose first block of variables holds
  the colors and the corner radius everything else is drawn with. The text is in
  `src/main/l10n`, in English, Spanish, French, German and Hebrew. The
  translations are machine-generated samples that no native speaker has
  reviewed; have them checked before you ship.
  What it reports to Codename One analytics about how it is used, once the user
  has agreed, is all in `Telemetry`.

| `backend`
| The server: accounts and roles, phone verification, the public keys of each
  device, conversations and their members, the envelopes that carry messages and
  their delivery over a WebSocket and push, encrypted attachments, call
  signalling and TURN credentials, reports and moderation, statistics, and the
  optional bridges to Telegram and WhatsApp.
  The data is entity classes in `domain`, read and written by the repository
  beside each service. The schema is the migration scripts in
  `src/main/resources/db/migration`, and the same server runs on SQLite,
  PostgreSQL, MySQL and MariaDB.

|===

There are no platform modules: `common` builds the application for the
simulator, the desktop, Android, iOS and the browser itself.

== Running it

Start the server on the development profile. It needs nothing installed: the
database is in memory, and text messages are printed on the console.

[source,bash]
----
CN1_PROFILE=dev backend/server.sh run
----

Then run the application in the simulator, from another terminal:

[source,bash]
----
mvn verify -Psimulator -DskipTests -Dcodename1.platform=javase
----

The development profile creates these accounts, all with the password
`parley-demo`, a few conversations between them and a bot that answers:

[cols="2,3"]
|===
| `alice@parley.example`, `bob@parley.example`, `carol@parley.example`, `dan@parley.example`
| users who share a group, a family group and a channel
| `mallory@parley.example` | a user an administrator has flagged, with a report open
| `admin@parley.example` | runs the service
|===

Sign in as one account in the simulator and as another in a second simulator or in
a browser to see a conversation from both ends. The bot answers whoever writes to
it, so one person trying the app alone has someone to talk to; its chat is plain
text, and the app says so. On a phone, set the server's address on the welcome
screen: `localhost` on a phone is the phone.

=== In a browser, with nothing installed

The server can host the application itself. Build the browser version once, and
again when the application changes; it takes about a minute:

[source,bash]
----
backend/server.sh web
CN1_PROFILE=dev backend/server.sh run
----

Then open `http://localhost:8080/`. `server.sh run --web` does both in one step.

`server.sh web` runs `cn1:backend-webapp`, which builds the application for the
browser and stages it in `backend/target/webapp`; a server that finds it there
serves it at `/`, after its own routes. In the browser the application takes the
page's address as the server's, signs in through the same authorization-code
flow with the code sent back to `/signin/code` on that server, and opens its live
channel to the same origin. To deploy it, put `backend/target/webapp` beside the
server binary as `webapp`.

A browser is linked as one more device of the account, with keys of its own. It
gives a page less than a phone gives an app, and the application says so where it
matters: the system call screen and the call push are for phones.

== What each role does

A user finds people by name, username or phone number and starts a chat, makes a
group of up to 256 people, or joins one with an invite link. A channel is a group
in which only the administrators can send. A conversation shows typing, delivery
and read state, and a message can be replied to, forwarded, edited and deleted for
everyone. Photos, video and voice notes are encrypted on the device before they are
uploaded. The conversation's info screen shows the safety numbers to compare with
the other person, a timer for disappearing messages, and the choice to block or
report. The settings hold the privacy choices -- who sees last seen and the photo,
read receipts, typing indicators, app lock and screen security -- and the linked
devices: up to six phones, tablets and browsers, each with keys of its own.

A call is one to one, voice or video, and rings on the lock screen through the
system call UI, with a VoIP push when the app is not running.

An administrator sees the service in charts of what the server can count,
resolves the reports people make, flags or blocks an account with a reason that is
kept in its history, names other administrators, and sees the conversations linked
to Telegram or WhatsApp.

== How the encryption works

Parley follows Signal's published X3DH and Double Ratchet specifications over the
primitives Codename One has on every port: P-256 for the Diffie-Hellman steps,
HKDF-SHA-256 for the key chains and AES-256-GCM for the messages. Every device is
its own identity, with an identity key, a signed prekey and one-time prekeys whose
private halves live only in an encrypted vault on the device. A message is
encrypted separately for each device of each recipient, and of the sender, so there
is no group key. The server stores envelopes it cannot open, and an attachment is
encrypted with a fresh key that travels inside the message. Users compare safety
numbers to know nobody is in the middle. The implementor's guide has the details.

The conversations that are not end-to-end encrypted are the demo bot's, and any
conversation an administrator links to Telegram or WhatsApp: a bridge has to read a
message to carry it, so such a conversation sends its messages to the server in
plain text, and the app marks it and tells its members when it is linked.

== What is real and what is simulated

Text messages go through the provider `parley.sms.provider` names: `twilio`,
`vonage` or `messagebird`, each with its own credentials. On a development
profile they are printed on the console instead, and the app is handed the code
so a sign-up can finish. Any other profile needs a provider; one whose
credentials are missing is logged as a configuration error, naming the missing
settings, and the app is told the code could not be sent.

Push goes through `parley.push.provider`: `cloud`, which sends through Codename
One's push servers with `parley.push.app` and `PARLEY_PUSH_KEY`, or `console` on a
development profile. A push never carries a message; it only wakes the app, which
fetches what is waiting and decrypts it on the device.

Calls connect the two phones directly when they can and through a TURN server when
they cannot. The server hands out the addresses with `parley.ice.stun` and
`parley.ice.turn`, and issues a credential per call that expires after
`parley.ice.ttl` seconds from the secret it shares with the TURN server
(`parley.ice.secret`, coturn's `static-auth-secret`). Without a TURN server only
STUN is offered, and calls between networks that block a direct path fail. In the
simulator the WebRTC package connects calls without carrying media, and the video
views show a test pattern.

The bridges are off until they are configured: `parley.telegram.token`,
`parley.telegram.secret` and `parley.telegram.bot` for a Telegram bot, whose
webhook is `/bridge/telegram/<secret>`, and `parley.whatsapp.token`,
`parley.whatsapp.phone`, `parley.whatsapp.secret` and `parley.whatsapp.verify` for
the WhatsApp Cloud API, whose webhook is `/bridge/whatsapp`.

`backend/application.properties` lists every setting a deployment supplies. The
database is the one named by `DATABASE_URL`: a `postgres://` or `mysql://`
address, or the path of a SQLite file. The settings are also read from the
environment in upper case with `_` for every dot (`PARLEY_SMS_TWILIO_TOKEN`).

== Tests

[source,bash]
----
mvn -pl shared,backend -Dcodename1.platform=backend test   # <1>
mvn -pl shared,backend -Dcodename1.platform=backend test -Dcn1.backend.compiledTests=true   # <2>
./run-e2e.sh   # <3>
./check-template.sh   # <4>
./run-web-e2e.sh   # <5>
----
<1> The server's tests, on the JVM.
<2> The same tests again, translated to a native binary, which is how the server
    ships.
<3> Starts the server on the `test` profile and runs the application's tests
    against it in the simulator, and compares the screens in `screenshots/`. Pass `--native` to run them against the compiled
    server. On Linux they then run a second time with the simulator as a desktop
    window, where the admin console is laid out side by side under the
    platform's own theme.
<4> Generates a project from the Initializr template, under another name and
    package, and builds it.
<5> Builds the browser version of the application, starts the server hosting
    it, and drives it in a headless browser: the application loads from the
    server, signs in as a demo user, links itself as a device, reaches the chat list and
    opens its live channel, then signs out and signs in as the demo admin. Needs Node with Playwright and its Chromium (`npm ci` and
    `npx playwright install chromium` in `scripts/`). Screenshots and logs go
    to `target/web-e2e`.

`.github/workflows/parley.yml` runs all five, and builds the application for
Android and iOS through `scripts/build-android-app.sh` and
`scripts/build-ios-app.sh` with `CN1_APP_DIR=scripts/parley`.

== The Initializr template

`scripts/sync-initializr-template.py parley --write` copies this project into the
Initializr's resources; without `--write` it fails when they differ, which is what
CI runs. Change the project here, never the copies.
