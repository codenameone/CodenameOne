= Pulse

A fitness studio's application and its server, in one Maven project and one
language. Members book classes for themselves and their children, open the door
with a pass on their phone or a fob, pay for their membership and keep up with
their friends; trainers run their classes and see who is in the zone; the front
desk lets people in and takes walk-ins; the owner reads the numbers and fills the
quiet classes. Which of these a person sees is decided by the roles the server
gives their account, and a tablet by the door runs the same app as a kiosk.

It is a sample of how a Codename One application and a Codename One Backend fit
together, and of the health, wearable, NFC and code-scanning APIs a studio app
reaches for.

== The modules

[cols="1,4"]
|===
| `shared`
| The contract: the data classes both sides exchange and the `@RestClient`
  interfaces that name every call. The app's build generates a client from them
  and the server's build generates the interfaces it implements, so a change the
  other side did not follow is a compile error.

| `common`
| The application: sign-in, the member, trainer, desk, kiosk and owner screens,
  the door pass, the wallet, the settings and the live channel. Styled in
  `src/main/css/theme.css`. The text is in `src/main/l10n`, in English,
  Spanish, French, German and Hebrew; the translations are machine-generated,
  so have them checked before you ship. What it reports to Codename One
  analytics about how it is used, once the user has agreed, is all in
  `Telemetry`.

| `backend`
| The server: accounts and roles, phone verification, households and their
  children, the timetable, bookings and the waitlist, door passes and
  check-ins, walk-ins, trainers' rosters and shifts, live heart rates,
  memberships and billing, away periods, nudges and campaigns, friends and
  kudos, the owner's dashboard, and a WebSocket that pushes changes as they
  happen. The data is entity classes in `domain`, read and written by the
  repositories in `repository`. The schema is the migration scripts in
  `src/main/resources/db/migration`, and the same server runs on SQLite,
  PostgreSQL, MySQL and MariaDB.
|===

There are no platform modules: `common` builds the application for the
simulator, the desktop, Android, iOS and the browser itself.

== Running it

Start the server on the development profile. It needs nothing installed: the
database is in memory, text messages and push notifications are printed on the
console, and cards are simulated.

[source,bash]
----
CN1_PROFILE=dev backend/server.sh run
----

Then run the application in the simulator, from another terminal:

[source,bash]
----
mvn verify -Psimulator -DskipTests -Dcodename1.platform=javase
----

The development profile creates a studio with two locations, a timetable of
adult and children's classes from three weeks back to three weeks ahead, the
plans on sale, and these accounts, all with the password `pulse-demo`:

[cols="2,3"]
|===
| `member@pulse.example` | a member with two children in their household and a card on file
| `member2@pulse.example` | a new member: no household, no card
| `member3@pulse.example` | a member the owner has flagged
| `member4@pulse.example` | a member who has not been in for weeks, for the we-miss-you nudge
| `trainer@pulse.example`, `trainer2@pulse.example` | teach classes
| `desk@pulse.example` | works the front desk and the door kiosk
| `owner@pulse.example` | runs the studio
|===

On a phone, set the server's address on the welcome screen: `localhost` on a
phone is the phone.

=== In a browser, with nothing installed

The server can host the application itself. Build the browser version once, and
again when the application changes:

[source,bash]
----
backend/server.sh web
CN1_PROFILE=dev backend/server.sh run
----

Then open `http://localhost:8080/`. `server.sh run --web` does both in one step.

== What each role does

A member books a place in a class, or joins its waitlist when it is full, and is
moved into the class the moment someone gives a place back. They book for their
children too: each child has their own membership, place and door pass, and the
classes offered are the ones their age fits on the day. The door pass is a QR
code that changes every 30 seconds and works with no signal, or an NFC fob for a
child without a phone. Members join, change, freeze and cancel plans, declare
when they will be away, add friends, give kudos and invite a friend to a class.
Workouts arrive from the phone's health store and the watch.

A trainer sees the week's classes, who is booked, who is waiting and who came,
marks attendance the door missed, follows each member's heart rate zone live
during a class, and offers shifts to the other trainers or takes theirs.

The front desk checks people in by scanning a pass, reading a fob or finding the
member by name, and every refusal comes with the reason to read out. It records
walk-ins: guests, day passes and free trials. A tablet signed in as the desk runs
as the kiosk by the door.

The owner reads monthly recurring revenue, utilisation, the members at risk of
leaving and the classes still under half full, edits plans, the timetable and
the staff, and sends campaigns.

== What is real and what is simulated

Text messages go through the provider `pulse.sms.provider` names: `twilio`,
`vonage` or `messagebird`, each with its own credentials. On a development
profile they are printed on the console instead, and the app is handed the code
so a sign-up can finish. Any other profile needs a provider; one whose
credentials are missing is logged as a configuration error, naming the missing
settings.

Payments are simulated on a development profile: the card
`4242 4242 4242 4242` is accepted, `4000 0000 0000 0002` is declined, and no
money moves. With `pulse.payments.provider=stripe` and
`PULSE_PAYMENTS_STRIPE_SECRET` set in the server's environment, a card is added
on Stripe's own page, so its number never reaches the app or this server.

Push notifications go through the Codename One push service with
`pulse.push.provider=cloud`, `pulse.push.app` and `PULSE_PUSH_KEY`.

`backend/application.properties` lists every setting a deployment supplies. The
database is the one named by `DATABASE_URL`: a `postgres://` or `mysql://`
address, or the path of a SQLite file. Every setting is also read from the
environment in upper case with `_` for every dot (`PULSE_SMS_TWILIO_TOKEN`).

== Tests

[source,bash]
----
mvn -pl shared,backend -Dcodename1.platform=backend test   # <1>
mvn -pl shared,backend -Dcodename1.platform=backend test -Dcn1.backend.compiledTests=true   # <2>
../ci/sample-server-tests-on-database.sh .   # <3>
./run-e2e.sh   # <4>
./run-web-e2e.sh   # <5>
----
<1> The server's tests, on the JVM.
<2> The same tests again, translated to a native binary, which is how the server
    ships.
<3> The server's tests against PostgreSQL or MySQL, named by
    `CN1_TEST_DATABASE_URL`.
<4> Starts the server on the `test` profile and runs the application's tests
    against it in the simulator. Pass `--native` to run them against the
    compiled server.
<5> Builds the browser version of the application, starts the server hosting
    it, and drives it in a headless browser. Needs Node with Playwright and its
    Chromium (`npm ci` and `npx playwright install chromium` in `scripts/`).

`.github/workflows/pulse.yml` runs them, and builds the application for Android
and iOS through `scripts/build-android-app.sh` and `scripts/build-ios-app.sh`
with `CN1_APP_DIR=scripts/pulse`.
